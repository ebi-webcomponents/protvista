# Architecture audit

This document is the planning artefact for two Q1 grant deliverables (SSI / RSMF, AH/Z000114/1, ROADMAP section Q1 Technical foundations): _"Architecture: identify hardcoded assumptions and create a removal plan"_ (issue #98) and _"Backwards compatibility: define compatibility promise for grant changes"_ (issue #102). It enumerates the hardcoded assumptions in the `protvista-uniprot` baseline tree at the start of the grant period, classifies each as **must-remove**, **nice-to-have**, or **keep-for-compatibility**, sets out a removal approach for each must-remove item, and records the compatibility surface and mitigation policy that fall out of the keep-for-compatibility category. It accompanies the v5 release work as the architectural reference for both the audit and the compatibility contract.

## Scope and method

**Baseline.** The audit is taken against `main` after the `testing-baseline` work merged. That commit is the reference point for the baseline state.

**Sources surveyed.** `src/config.ts` (the 912-line TypeScript config that defines the 15 UniProt groups and their tracks), `src/protvista-uniprot.ts` (the element class, including its `_loadData()` pipeline and `registerWebComponents()` method), the eleven adapters under `src/adapters/`, the six imperative tooltip builders under `src/tooltips/`, the styles in `src/styles/`, and the security helpers in `src/utils/security.ts`.

**Categorisation rubric.**

- **must-remove** — explicitly in the grant's Q1 scope: "decoupling ProtVista from hardcoded EBI infrastructure" and "mount tracks dynamically based on a user-provided configuration file rather than hardcoded group lists". An external embedder cannot adopt ProtVista for non-UniProt data while this assumption stands.
- **nice-to-have** — not strictly required to satisfy Q1, but a foreseeable obstacle for a meaningful subset of adopters. Captured as a follow-on issue with explicit grant-period intent (Q2/Q3) or post-grant.
- **keep-for-compatibility** — deliberately retained. Either (a) an external contract whose removal would break the published API surface, (b) an upstream constraint owned by `@nightingale-elements/*` rather than this package, or (c) intrinsic to the product (e.g. the element name `protvista-uniprot`).

## Findings

### A. must-remove (Q1 scope)

| #   | Hardcoded assumption                                                                                                                                                                                      | Removal approach                                                                                                                                                                                                                                                                                                             |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | Four EBI API base URLs (`proteins`, `alphafold`, `alphafoldEntry`, `interpro`) baked into `src/config.ts` as module-level constants.                                                                      | URLs live in a named `sources:` block in a user-supplied YAML/JSON config. Embedders supply their own; the schema accepts arbitrary URL templates.                                                                                                                                                                           |
| A2  | A 912-line hand-rolled `categories` array enumerating 15 groups and ~40 tracks, each with hardcoded `name`, `label`, `trackType`, `data[].url`, `data[].adapter`, `tooltip`, `helpPage`, `filter`.        | The config is a declarative YAML document consumed by a parse → extends → validate → normalize → load pipeline. Tracks mount from any config conforming to a published JSON schema. The UniProt content lives in the bundled `default-config.yaml`.                                                                          |
| A3  | A closed `TrackType` string-literal union of nightingale component names. Adding a component requires a TypeScript edit to the consumer.                                                                  | `ComponentName` is `KnownComponentName \| (string & {})` so the literal union keeps autocomplete while accepting consumer-registered names. New components register at runtime via a `registerSemanticKind()` API.                                                                                                           |
| A4  | A closed `adapter` string-literal union (twelve EBI-specific names) on `ProtvistaTrackConfig.data[].adapter`.                                                                                             | Same treatment as A3 — `AdapterName` is `KnownAdapterName \| (string & {})` with built-ins seeded by a `registerBuiltinAdapters()` call at loader init; consumer adapters register via an `element.registerAdapter()` API.                                                                                                   |
| A5  | A single static `adapters: Record<string, Function>` map in the element file, with adapter wiring duplicated between `config.ts` and `protvista-uniprot.ts`.                                              | Adapter resolution lives in a per-instance `Registry`; the loader looks adapters up by name at fetch time. The duplication and cross-file invariant fall away.                                                                                                                                                               |
| A6  | The track→component mapping is implicit in each track definition (`trackType: 'nightingale-track-canvas'` etc.) and has to be repeated by every author.                                                   | **Semantic kinds** (`features`, `variants`, `confidence-score`, …) form a small closed enumeration. Authors write `kind: features`; the registry resolves the name to `(component, adapter, rendering preset)`.                                                                                                              |
| A7  | Hardcoded AlphaFold and AlphaMissense colour ramps (pLDDT bins, pathogenicity bins) embedded in the element import (`amColorScale`) plus inline track definitions with `scale:` / `color-range:` strings. | Colour ramps are first-class **themes** (`alphafold-ramp`, `alphamissense-ramp`) attached to the relevant semantic kinds as canonical rendering presets. Consumer-defined ramps register via `element.registerTheme()`.                                                                                                      |
| A8  | The `{accession}` URL placeholder is substituted by an inline `url.replace('{accession}', accession)` call buried in `_loadData()`. No documented contract; no other variables supported.                 | Substitution lives in the loader, with `{accession}` documented as the stable placeholder. Generalisation to arbitrary `data-*` variables is Q2 follow-on work (see B2).                                                                                                                                                     |
| A9  | Per-feature **tooltip HTML built imperatively** in five `src/tooltips/*-tooltip.ts` files — string-concatenated HTML, hardcoded source-icon URLs, baked-in EBI cross-reference rules.                     | The tooltip resolver is declarative: `kind: 'fields'` (deterministic HTML synthesis from `{path,label}` rows) or `kind: 'markdown'` (Markdoc template against the item's payload + a small `ctx` object). Per-track override via `dataTooltip:`; consumer-side rich tooltips via the `notooltip` attribute + `change` event. |
| A10 | `taxIdToPeptideAtlasBuildData` and `unimodIdMapping` lookup tables embedded in `feature-tooltip.ts` — UniProt-specific PeptideAtlas/UNIMOD knowledge, bundled into every consumer.                        | The lookup tables fall away with the imperative tooltip layer. Equivalent context becomes part of the adapter's payload or is supplied via `dataTooltip` Markdoc templates that consumers can override per track.                                                                                                            |
| A11 | The variation-filter UI assumes a track with id `variation` exactly, and stashes transformed variants on `this.transformedVariants` for the filter to read.                                               | The side-effect is preserved through the refactor: the element reads `data['VARIATION-variation']` after the pure-function load. Lifting the hardcoded id match is Q2 follow-on work (see B3).                                                                                                                               |
| A12 | The element registers a fixed list of nightingale custom-element tags via a `registerWebComponents()` method on the class — no extension point.                                                           | Component registration goes through the registry's resolution path so consumer-defined kinds can bring their own component tags. Initial scope keeps the existing `registerWebComponents()` call for the built-in nightingale set; full registry-driven `customElements.define()` is Q2 follow-on work (see B18).            |
| A13 | Specs-as-comments — source files reference internal task numbers and `specs/*.md` paths (`// see specs/X.md, section 3`), creating a maintenance dependency on volatile design docs.                               | Code stands alone; spec files may point at code, not the other way. Source comments restate the relevant claim in plain English.                                                                                                                                                                                             |
| A14 | Global `<style>` injected on every constructor call, with selectors that leak beyond the element's own subtree.                                                                                           | Styles are scoped under the `protvista-uniprot` tag selector; `addStyles()` is guarded against double-install. CSS class-name namespacing with a `pv-` prefix is the remaining piece (see B9).                                                                                                                               |

These are hardcoded assumptions whose removal is not strictly required to make ProtVista config-driven for an external embedder, but each one papers over a specific class of adopter friction. All are filed as GitHub issues under the [`next` label](https://github.com/ebi-webcomponents/protvista-uniprot/issues?q=label%3Anext) with a default project-board target of `Quarter: Q2 (May–Jul 2026)`.

| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |

| B14 | Errors during config load / fetch fall through to an empty-state render with no user-facing diagnostic.                                                                                                                                           | [#158](https://github.com/ebi-webcomponents/protvista-uniprot/issues/158) |
| B15 | Dev-server first visit often fails to load data; hard refresh required.                                                                                                                                                                           | [#159](https://github.com/ebi-webcomponents/protvista-uniprot/issues/159) |

| B17 | No reproducible Linux dev environment for contributors on non-macOS hosts.                                                                                                                                                                        | [#151](https://github.com/ebi-webcomponents/protvista-uniprot/issues/151) |

### C. keep-for-compatibility

**Compatibility surface.** The compatibility contract for the v5 cycle covers: the `<protvista-uniprot>` element tag and the `protvista-uniprot` npm package name; the public runtime API methods (`registerSemanticKind`, `registerAdapter`, `registerTheme`, plus a future `registerComponent`); the field names and shapes in `src/schema/schema.json`; the `change` event payload (the `detail.eventType` vocabulary, `detail.feature`, `detail.coords`); and the verbatim track-id strings in the bundled default config. CSS class names, internal module structure, and intermediate adapter outputs are _not_ part of the contract and may change without notice.

**Mitigation.** All the breaking changes for the v5 release ship together in v5.0.0 — never in a v4.x patch release. They live on the `next` branch for at least three months before merging to `main`, giving consumers time to see what's coming and prepare. Later major releases may follow a different schedule depending on team capacity. Each breaking change is filed as a follow-on issue under the [`next` label](https://github.com/ebi-webcomponents/protvista-uniprot/issues?q=label%3Anext) with its migration path written into the issue body.

| #   | Hardcoded assumption                                                                                                                                                                            | Why kept                                                                                                                                                                                                                                                                                                                                                              |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C1  | The custom-element tag name `<protvista-uniprot>` and the published npm package name `protvista-uniprot`.                                                                                       | External contract for the v4 → v5 transition. A rename to the generic `protvista` package name and a non-UniProt-coupled tag is under consideration for the v5 cycle (see #164). If adopted, both the existing tag and the existing package name will be preserved as transitional aliases for one major-version cycle so v4 consumers can migrate at their own pace. |
| C2  | Rendering goes through `@nightingale-elements/*` Lit components (canvas / track / variation / linegraph / sequence-heatmap).                                                                    | Upstream package boundary. The ROADMAP explicitly notes that rendering improvements (Canvas/WebGL) are owned by Nightingale and require coordinated upstream changes; not in this package's scope.                                                                                                                                                                    |
| C3  | The closed enumeration of built-in semantic kinds in `KnownSemanticKind`.                                                                                                                       | Closed for IntelliSense / type-safety on the _known_ names; open at runtime via `(string & {})` and `registerSemanticKind()`. Closing the literal union is what gives editors useful autocomplete.                                                                                                                                                                    |
| C4  | `js-yaml`'s `SAFE_SCHEMA` (no `!!js/function`, no surprise tag handlers) is the only YAML-tag policy supported.                                                                                 | Security boundary. The parser is deliberately minimal; broader tag handling would re-open author-controlled-code injection.                                                                                                                                                                                                                                           |
| C5  | URL schemes `http:`, `https:`, `mailto:` only — `javascript:` and `data:` URLs are dropped at render time.                                                                                      | Security boundary (`src/utils/security.ts`). XSS regression suite locks this in.                                                                                                                                                                                                                                                                                      |
| C6  | The default config bundles the EBI UniProt API as the data source.                                                                                                                              | A _default_ is not a hardcoding — overriding it is the supported flow. The default is what an embedder gets when they pass nothing; the canonical reference, not a constraint.                                                                                                                                                                                        |
| C7  | Track ids preserved verbatim from the legacy config (e.g. `'RNA Editing'` with the space, `'proteomics-ptm'` with the hyphen) even where they violate the recommended `lower_snake` convention. | External contract. The renderer's data-map keys (`${groupId}-${trackId}`) are observable to consumers; renaming silently would break anyone watching for specific track keys.                                                                                                                                                                                         |

## Acceptance criteria

The Q1 issue's acceptance criteria are:

- **Written list + categorisation.** Met by section A (must-remove), section B (nice-to-have), section C (keep-for-compatibility) above.
- **Follow-on issues created for each must-remove item.** section A items are addressed directly by the configuration-driven refactor merged via [PR #132](https://github.com/ebi-webcomponents/protvista-uniprot/pull/132) and staged on the `next` branch. Residual gaps from A8, A11, A12, and A14 are tracked as standalone follow-on issues [#153](https://github.com/ebi-webcomponents/protvista-uniprot/issues/153), [#156](https://github.com/ebi-webcomponents/protvista-uniprot/issues/156), [#161](https://github.com/ebi-webcomponents/protvista-uniprot/issues/161), and [#152](https://github.com/ebi-webcomponents/protvista-uniprot/issues/152) respectively. All section B items are filed as GitHub issues under the [`next` label](https://github.com/ebi-webcomponents/protvista-uniprot/issues?q=label%3Anext).
- section C compatibility decisions feed into [#102 (compatibility promise)](https://github.com/ebi-webcomponents/protvista-uniprot/issues/102).
