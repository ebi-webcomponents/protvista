# Architecture audit

This document is the architectural reference for two Q1 grant deliverables (SSI / RSMF, AH/Z000114/1, ROADMAP section Q1 Technical foundations): _"Architecture: identify hardcoded assumptions and create a removal plan"_ (issue #98) and _"Backwards compatibility: define compatibility promise for grant changes"_ (issue #102). It enumerates the hardcoded assumptions in the `protvista-uniprot` baseline tree at the start of the grant period, classifies each as **must-remove**, **nice-to-have**, or **keep-for-compatibility**, records the removal approach taken for each must-remove item, and sets out the compatibility surface and mitigation policy that fall out of the keep-for-compatibility category. It accompanies the v5 release work as the architectural reference for both the audit and the compatibility contract.

## Scope and method

**Baseline.** The audit is taken against `main` after the `testing-baseline` work merged. That commit is the reference point for the baseline state.

**Sources surveyed.** `src/config.ts` (the 912-line TypeScript config that defines the 15 UniProt groups and their tracks), `src/protvista-uniprot.ts` (the element class, including its `_loadData()` pipeline and `registerWebComponents()` method), the eleven adapters under `src/adapters/`, the six imperative tooltip builders under `src/tooltips/`, the styles in `src/styles/`, and the security helpers in `src/utils/security.ts`.

**Categorisation rubric.**

- **must-remove** — explicitly in the grant's Q1 scope: "decoupling ProtVista from hardcoded EBI infrastructure" and "mount tracks dynamically based on a user-provided configuration file rather than hardcoded group lists". An external embedder cannot adopt ProtVista for non-UniProt data while this assumption stands.
- **nice-to-have** — not strictly required to satisfy Q1, but a foreseeable obstacle for a meaningful subset of adopters. Captured as a follow-on issue with explicit grant-period intent (Q2/Q3) or post-grant.
- **keep-for-compatibility** — deliberately retained. Either (a) an external contract whose removal would break the published API surface, (b) an upstream constraint owned by `@nightingale-elements/*` rather than this package, or (c) intrinsic to the product (e.g. the element name `protvista-uniprot`).

**Status (Q3 check, #380).** The _Status on `next`_ column in tables A and B records each item as of `next` at `8c63ece` (29 October 2026), except A1, A7 and A13, rechecked at `09f1832` (30 October 2026) after their fixes merged. For an A item, "Removed" means the assumption was searched for in `src/` on that commit and not found, and the link is the PR (and commit) that removed it, found with `git log -S`. For a B item, the status is its GitHub issue's state, linked to the PR that closed it. [Legacy browser workarounds](#legacy-browser-workarounds) records the same check for browser-support code.

### C. keep-for-compatibility

**Compatibility surface.** The compatibility contract for the v5 cycle covers: the `<protvista-uniprot>` element tag and the `protvista-uniprot` npm package name; the public runtime API methods (`registerSemanticKind`, `registerAdapter`, `registerTheme`, plus a future `registerComponent`); the field names and shapes in `src/schema/schema.json`; the `change` event payload (the `detail.eventType` vocabulary, `detail.feature`, `detail.coords`); and the verbatim track-id strings in the bundled default config. CSS class names, internal module structure, and intermediate adapter outputs are _not_ part of the contract and may change without notice.

**Mitigation.** All the breaking changes for the v5 release ship together in v5.0.0 — never in a v4.x patch release. They live on the `next` branch for at least three months before merging to `main`, giving consumers time to see what's coming and prepare. Later major releases may follow a different schedule depending on team capacity. Each breaking change is filed as a follow-on issue under the [`next` label](https://github.com/ebi-webcomponents/protvista-uniprot/issues?q=label%3Anext) with its migration path written into the issue body.

The parser is deliberately minimal; broader tag handling would re-open author-controlled-code injection.                                                                                                                                                                                                                                           |
| C5  | URL schemes `http:`, `https:`, `mailto:` only — `javascript:` and `data:` URLs are dropped at render time.                                                                                      | Security boundary (`src/utils/security.ts`). XSS regression suite locks this in.                                                                                                                                                                                                                                                                                      |
| C6  | The default config bundles the EBI UniProt API as the data source.                                                                                                                              | A _default_ is not a hardcoding — overriding it is the supported flow. The default is what an embedder gets when they pass nothing; the canonical reference, not a constraint.                                                                                                                                                                                        |
| C7  | Track ids preserved verbatim from the legacy config (e.g. `'RNA Editing'` with the space, `'proteomics-ptm'` with the hyphen) even where they violate the recommended `lower_snake` convention. | External contract. The renderer's data-map keys (`${groupId}-${trackId}`) are observable to consumers; renaming silently would break anyone watching for specific track keys.                                                                                                                                                                                         |

## #159 reproduction

[#159](https://github.com/ebi-webcomponents/protvista-uniprot/issues/159) (B15) reported that the first visit to the dev server often loaded no track data until a hard refresh. It was closed on 21 July 2026 as probably fixed by [#198](https://github.com/ebi-webcomponents/protvista-uniprot/pull/198), with no reproduction recorded. The command it described, `yarn start`, has since become `pnpm start`, which runs the Astro docs site and its playground ([#239](https://github.com/ebi-webcomponents/protvista-uniprot/pull/239), [#267](https://github.com/ebi-webcomponents/protvista-uniprot/pull/267)).

**What was done** (29 October 2026, Linux sandbox, Node 24.22, pnpm 12.4):

1. A clean worktree of `next` at `8c63ece`; `pnpm install --frozen-lockfile`.
2. Deleted Vite's dependency cache (`node_modules/.vite`) so the dev server started cold, then ran `pnpm start` with `ASTRO_DEV_BACKGROUND=1`. (Without it, Astro detects an agent, starts itself in the background and gives up after 30 s; on this heavily loaded machine it needed 63 s.)
3. A Playwright script opened `http://localhost:4321/protvista/playground/` (the default preset: the bundled default config, accession P05067) in headless Chromium, three times, each in a new browser context: empty HTTP cache, service workers blocked. It waited up to 60 s for the element's `data` to fill, then 5 s more, and recorded failed requests and console errors.

**What was seen.** On the first visit the page took 52 s to load while Vite bundled its dependencies. The optimiser did not trigger a page reload. Track data then arrived about 4 s after the load event, with no refresh: 42 of the 62 track data keys held data. The second and third visits loaded in 1–2 s and filled the same 42 keys. Every visit had the same three failed requests: AlphaFold DB `prediction/P05067` (two requests, HTTP 403) and `rna-editing/P05067` (HTTP 404, P05067 has no RNA-editing data).

**Limits.** The sandbox's network proxy drops Chromium's own connections to `www.ebi.ac.uk` (every request failed with `ERR_HTTP2_PROTOCOL_ERROR`, or `ERR_EMPTY_RESPONSE` with HTTP/2 off), so the script relayed EBI requests through Node's `fetch` and returned the responses to the page. Response timing therefore differs from a real browser on an open network, and the AlphaFold 403s may come from the proxy. One machine and one browser engine were tested.

**Result.** Not reproduced: data loaded on first navigation of a cold dev server in all three runs. #159 stays closed. Anyone who sees the symptom again should reopen it with a network log recorded from before the page request, as the issue asks.
